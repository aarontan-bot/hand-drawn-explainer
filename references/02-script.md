# 阶段 2 · 脚本：从知识真相源到可制作的分镜脚本

输入：`_grounding/知识底座稿.md` 或用户给的知识稿（下称**真相源**）。输出：`脚本/00-全片设定.md`、每集 `<集号>-<标题>.md`、`分集建议.md`、`脚本审阅版.html`。本阶段不配音、不出图、不渲染。

## 七步
| 步 | 做什么 | 谁做 | 产出 |
|---|---|---|---|
| 1 | **吸收判断**：读预设的判例库（若有）与上一个同预设项目 spec 的「判断规则」段，直接继承 | 主循环 | spec 的「判断规则」段 |
| 2 | **全片设定**：角色（可无）、画风、镜头语汇、片头片尾、屏幕文字规则、贯穿句 | 主循环 | `00-全片设定.md`（[templates/series-setup.md](../templates/series-setup.md)） |
| 3 | **逐集写稿**：按集号顺序亲自写，写完一集存一集；写下一集前重读全片设定防口吻漂移 | **主循环亲自写** | 每集脚本（[templates/script-section.md](../templates/script-section.md)） |
| 4 | **机器扫**：`python3 $HDE/lib/lint_script.py 脚本/` | 主循环 | 0 条红线才进下一步 |
| 5 | **三路并行审稿**：对账 / 受众视角 / 规则与风格 | 派 3 个 agent | 三份问题清单（[02-review-briefs.md](02-review-briefs.md)） |
| 6 | **统改 + 对账**：裁决三路冲突 → 改上游（spec / 全片设定）→ 改脚本 → `python3 $HDE/lib/retime.py 脚本/` 回填时间码 → 对 spec 验收清单逐条核 | 主循环 | 定稿 + 对账结果 + spec「统改裁决」段 |
| 7 | **分集建议 + 审阅版**：`python3 $HDE/lib/build_reader.py 脚本/` | 主循环 | `分集建议.md`、`脚本审阅版.html` |

第 3 步必须主循环亲自写：万字级长稿派子 agent 会被截断、口吻会漂移。派工只用于机械活。

## 写作原则（决定好坏；每集写完用末尾清单自查）
1. **处境开场**：把观众放进一个具体场景或麻烦，再给概念；定义要像"回答观众已经有的问题"。有固定角色就让角色遇到麻烦。
2. **一条脊柱**：整集回答一个问题或走完一段旅程，每节是脊柱上的一步。测试：各节能随意换序而不损失，就是没有脊柱，回去重找。**真相源是逐节细表，照它的目录顺序复述就会变成工具清单**，这是最常见的失败。
3. **先因后果**：每个点按"没有它会怎样 → 它怎么工作 → 得到什么"讲；砍篇幅时先砍机制细节，留"为什么"。
4. **数字可感**：每个数字换算成受众身边的尺度，换不出来就删。易变数字加限定（"发布时""某一款"）。
5. **比喻承重**：只在能帮观众推理时用比喻，用了就贯穿到底；不按节配比喻，符号（灯泡、乌云、星星）每集最多一次。
6. **先总览后细节**：每集一张总览图，旁白一句带过，不念"今天讲 N 件事"。
7. **术语后置**：先用人话把事说明白，再挂名字；每个名字后面必须再用一次。**撑讲解的日常词比术语更要命**（"模型""特征""机制""原始数据"这类），开写前列出来，要么先解释一句要么换成人话。
8. **清单不逐条念**：五条以上按共同点分成 2–3 组，每组给一个共同办法。
9. **节奏有变化**：长句后接短句，问一句停一拍再揭晓；连续三句同长同形就改一句。
10. **结尾回扣**：回到开场的处境，用新理解重说一遍；不是总结清单，不是告别。
11. **只说画面说不了的**：旁白讲原因、后果、比较、判断；画面承担结构、顺序、数量。不念画面（"这里我们看到"）。
12. **精确换信任**：真名、真数、来源可查；近似标近似；不把事实圆成口号。

## 硬规则（红线；`lint_script.py` 能扫的它扫，扫不了的审稿查）
1. **旁白是给人读的原文**，逐字可合成；数字写成读音顺的形式，屏幕文字保留原样。
2. **每镜标做法**：`插画` 或 `程序`。插画只画线稿和物体本身的少量颜色；圈框、箭头、问号、任何文字一律程序层。
3. **屏幕只放三类字**：原文引用、结果原文、2–8 字关键词。讲解都在旁白里。不上整张表，表格画成图逐行出现。
4. **每镜写出主图**：「画面」栏第一句说本镜主图是什么、占多大（约安全区高度的几分之几），其余部件围着它摆。
5. **颜色两层**：部件层同一底色 + 编号角标，不用颜色分部件；路径层每条路径一种颜色、全程同色；每种颜色的含义写在全片设定的颜色表里并跨集锁定（值不在本文档定）。
6. **来源处理按预设**，缺省：旁白、屏幕文字、片尾不出现原作者、论文题目、原课程名、厂商名，也不用"原材料提到"这类编写过程措辞；来源留在底座稿。
7. **数字不写死**：型号、尺寸上限、Token 数一律不点；只有真相源标为稳定的数字才能进脚本，并列进 spec 的稳定数字白名单。
8. **时间段不手算**：一律 `retime.py` 回填（手估字数系统性偏高 20–35%）。
9. **对账表分两区**：「真相源要点 → 镜号」和「本集 spec 要求 → 落在哪」分开写。
10. **受众红线按预设**：预设写了的逐条照办（通用版无）。

## 常见坑
- 真相源的「待确认事项」是雷：开工前逐条关闭或标"本轮按 X 处理，待拍板"。
- 真相源的时长是参考不是指标：实测都更短；不注水，偏差写进分集建议。
- 例子被写顺手改掉：对账审稿逐字核。
- 插画镜太密：情景、障碍、检查结果、转场用插画，机制讲解全交程序层。
- 出图清单里要求画字：生图模型会画伪字。出图描述一律不含文字要求，也不写"写字"这类动作。
- 最难的一集别开场砸新词：先用一个知识点解掉主角的麻烦，再由它往外推广。第一集是弃看率最高的一集。
- 三路审稿一定互相冲突（对账要贴原文、受众视角要听得懂）：主循环裁决，裁决写进 spec「统改裁决」段。
- 脚本与真相源的口径差异不擅自改真相源：列「需回写清单」进 spec，交付时请用户拍板。

## 移交契约（脚本定稿、用户逐集确认后才切到阶段 3）
- [ ] 每镜有：镜号、时间段、做法、旁白原文、画面说明（含主图）；需准确上屏的内容写在「屏幕文字」里。
- [ ] 每个插画镜在「出图清单」里有对应描述，不含文字要求。**两种写法都认**：三列 `| 镜号 | 左边 | 右边 |`（单幅右边写 `—`），或两列 `| 镜号 | 画面描述 |`（单元格里用「分两层：左层，…；右层，…」拆左右，也认 `左层：` / `左边：` / `LEFT：` 等写法；「单场景居中：…」或整段没有任何标记即单幅）。
- [ ] 旁白可直接拼成整集配音稿。
- [ ] 屏幕文字全部走程序层，没有指望生图模型写字的地方。
- [ ] 本集「一句话记住」与收尾回扣已写死，与真相源原文一致。
- [ ] `lint_script.py` 0 条红线；spec 验收清单逐条有对账结果。
- [ ] `python3 $HDE/lib/retime.py 脚本/ --check` 退出码 0（时间码与卡片字数确实回填过，不是手估的）。
